多步任务里，「一个 Agent 包打天下」和「十几个子 Agent 互相发消息」都容易翻车。拆子 Agent（Sub-agent）指的是：**按职责切出独立循环，各自有工具集与上下文，由协调者汇总**。

拆太碎，协调成本与 token 爆炸；不拆，单上下文里 Plan 会迷路、工具权限难收口。难点不在「能不能拆」，而在**边界画在哪**。

下面是我整理的拆分判断：何时保持单循环、何时拆、协调模式与坑。

拆与不拆没有银弹：同一产品里，「问答助手」可能单循环就够，「自动修 bug 机器人」往往值得流水线拆。用任务类型而不是组织职级来划边界，成功率更高。

![单 Agent 过载示意](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/single-agent-overload_cY2W7BAwrZ.png)

## 一、先说一个具体麻烦

你做一个「从需求到 PR」的 coding Agent：读 issue、搜代码、改文件、跑测试、开 PR、写说明。全塞进一个 loop。

跑复杂需求时，上下文里堆满无关检索片段；改到一半又去「优化 README」。测试红了，它却基于旧代码继续 patch——**不是模型笨，是单 Agent 同时背负规划、实现、评审三件事**。

日志里还会出现另一种症状：同一个文件被反复读写，因为 Observe 里的测试结果与编辑器状态不同步，Plan 误判「还没改对」。

## 二、先问三个问题再决定是否拆

（1）**工具集能否按风险分组？**  
只读检索与写库、发版若混在一起，适合拆；全是只读查询，单 Agent 往往够。  
（2）**中间产物是否需要不同格式的「专业深度」？**  
例如「检索证据」与「写补丁」对温度、系统提示要求不同，可拆。  
（3）**能否用明确接口传递状态？**  
子 Agent 之间若只能传自然语言小作文，拆了反而更乱；应定义 JSON 任务包。

![拆分子 Agent 的协调结构](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/split-agents_Vu9gHSqTy.png)

## 三、三种常见拆分模式

（1）**流水线式**  
检索 Agent → 实现 Agent → 测试 Agent，单向传递结构化结果。适合步骤顺序固定、可验收的中间件。  
（2）**协调者 + 工作者**  
主 Agent 只 Plan 与分派；子 Agent 各自 Plan-Act-Observe，回传摘要。适合任务类型多变。  
（3）**专家会诊式**  
并行多个只读 Agent（安全、性能、合规），协调者合并——适合 review 类，不适合强依赖顺序的写操作。

拆完还要算总账：多一次子 Agent 调用，就多一轮 Plan 与上下文序列化。若节省的 token 抵不过协调开销，就应回退单循环。

## 四、协调者该传什么

子 Agent 的输入最好是**任务契约**，而不是复制整段聊天史。

```json
{
  "task_id": "impl-42",
  "goal": "修复 login 超时：将会话 TTL 改为 3600",
  "constraints": ["仅改 auth/session.ts", "必须附带单测"],
  "inputs": {
    "relevant_files": ["auth/session.ts", "tests/session.test.ts"],
    "retrieval_summary": "设计文档 §3.2 规定 TTL 默认 3600"
  }
}
```

上面代码中，`retrieval_summary` 由检索子 Agent 产出，实现 Agent **不必**再搜一遍；`constraints` 让权限与范围在宿主侧可校验。

协调者收到子 Agent 结果后，应先做 schema 校验再合并——自然语言摘要若缺字段，就要求子 Agent 重发 JSON，而不是协调者自己脑补。

## 五、何时不要拆

（1）**总步数 ≤ 3 且工具 ≤ 5**  
单循环 + 好 schema 通常更省。  
（2）**强实时对话**  
用户期望一个「助手」连续交流，频繁子 Agent 交接 会增加延迟与口吻断裂。  
（3）**无法定义验收**  
拆出去的工作若不能 `pass/fail`，协调者无法 Observe，只会多一层幻觉。

若团队人手有限，优先把「协调者提示词 + 任务 JSON 契约」写稳，再考虑物理拆进程。过早微服务化 Agent，运维成本常常先于模型成本爆表。

## 六、常见误区

（1）**按组织架构拆**  
「前端 Agent」「后端 Agent」未必对应任务切分。  
（2）**子 Agent 权限与父级相同**  
拆分的意义之一是缩权限；见系列第十篇。  
（3）**无步数上限**  
协调者无限委派，费用与时间都不可控。  
（4）**子 Agent 输出不结构化**  
协调者再次用模型「读懂小作文」，错误累积。  
（5）**该拆却用超长上下文硬扛**  
见系列第二篇「上下文太长——砍什么、留什么」。

协调者与工作者共用同一模型时，记得给工作者**更窄的工具列表**；否则拆分只省字数，不省风险。

评测拆分时可看两个指标：单任务成功率，以及协调者「汇总结论与工作者日志是否一致」——后者抓的是接口层幻觉。

## 七、小结与系列导航

拆子 Agent 的本质：**用接口换专注，用协调换单上下文过载**。能结构化传递、能独立验收、能缩权限时再拆；否则先把单循环的 Plan-Act-Observe 与工具 schema 打磨好。协调者的质量，往往决定拆分是减负还是加倍。

若协调者本身就需要读十份中间产物，说明接口粒度过细——合并两步、减少 handoff，有时比再加一个子 Agent 更划算。
