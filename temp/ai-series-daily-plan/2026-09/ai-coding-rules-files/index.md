规则文件（如 `.cursorrules`、`AGENTS.md`）是写给模型的**长期 Grounding**：每次对话自动注入，告诉它「在这个仓库里怎么做事」。写对了省重复解释；写错了占上下文、还互相打架。

和 RAG 检索片段不同，规则文件是**固定约束层**。Agent 工程笔记里 Grounding 强调「只依据给定证据」——规则文件就是其中一层证据，但要短、硬、可执行，不能写成第二份 README。

我见过两种极端：一种是完全没有规则，每次对话重复「请用 pnpm、别改 lockfile」；另一种是规则写到上千行，把博客教程贴进去，结果真正有用的测试命令反而被挤到窗口外。两种都 Ground 不好。

下面是我维护规则文件的实践与反例。文中提到的 Grounding，与 Agent 工程笔记⑨同一套逻辑：规则是可被每次对话自动加载的证据，不是写给人类看的博客。

![规则文件分层：仓库、项目、会话](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/rules-layers_zANgNmmgi.png)

## 一、放哪、谁覆盖谁

常见三层：

（1）**仓库根 `AGENTS.md`**：全项目通用——语言、测试命令、目录约定、禁止事项。  
（2）**子目录或 `.cursorrules`**：模块特化——前端用 Tailwind、后端用特定 ORM。  
（3）**会话里临时一句**：本次任务边界，不写进文件。

原则：**越全局越稳定，越局部越具体**。不要把一次 PR 的临时决定写进根规则；也不要在每个子目录复制粘贴整份根规则。子目录规则只写**与根规则不同**的部分，例如「本包用 Vitest 而非 Jest」，避免重复占窗口。

## 二、该写什么

![规则文件该写与不该写](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/rules-scope_T6x1kaFNf.png)

我只写四类：

（1）**命令**：怎么装依赖、怎么跑测试、怎么构建。  
（2）**命名与结构**：文件放哪、组件怎么命名。  
（3）**硬约束**：不许改哪些目录、commit 语言、安全红线。  
（4）**Review 偏好**：小 diff、先测后交。

示例片段：

```markdown
## 测试
- 改 src/ 下逻辑必须跑：`npm test -- --runInBand`
- 不 mock 被测模块本身的业务分支

## 禁止
- 不修改 01-原始素材区/
- 不在规则里放密钥或 .env 内容
```

上面代码中，测试命令可**复制即跑**；禁止项避免 Agent 误动不可变数据。

好的规则像 lint 规则：**违反即错**，而不是「建议考虑」。我会定期把 CI 失败日志里反复出现、且与规则无关的问题，反过来问：是不是缺一条硬约束？若是，就补进 AGENTS.md，而不是在 chat 里第三次口头重复。

## 三、不该写什么

（1）整份 API 文档——应链到 `docs/`，需要时再 `@` 引用。  
（2）长篇教程——占窗口，且易过期。  
（3）与代码矛盾的描述——模型会猜该信哪边。  
（4）Secrets——规则文件常进 Git，泄漏风险高。  
（5）「尽量优雅」「注意性能」——没有验收标准，等于没说。  
（6）与另一规则文件矛盾的内容——合并前必须人工裁断，否则模型随机选边站。

规则文件也应像代码一样 review：新增一条规则，问「违反时 CI 能抓吗？不能的话是否值得占上下文？」

## 四、和 @ 引用的分工

规则文件回答「**默认怎么做**」；`@file` 回答「**这次看哪份材料**」。规则写「测试用 Jest」，具体用例仍靠 `@` 指向测试文件。上下文裁剪时，**规则层优先保留**，动态文件按需 `@`，这和 Grounding 里「证据层不能先删」同一逻辑。

## 五、从口头约束到规则文件

我的触发条件：

（1）同一句话在三次对话里重复 → 收进规则。  
（2）新人 onboarding 必问的命令 → 收进规则。  
（3）Agent 连续两次犯同类错（如改错目录）→ 加禁止项。

写完后用一个小任务试跑：新开对话，不给额外说明，看模型是否默认跑对测试、避对禁区。若仍反复犯错，不是再加长规则，而是检查规则是否可执行、是否与 CI 一致——模糊的规则对 Grounding 没有帮助。

## 六、维护节奏

（1）**规则超过 200 行** → 拆到子目录或 `docs/`。  
（2）**改架构后** → 同步改规则里过时的路径。  
（3）**季度扫一遍** → 删已不执行的条目。  
（4）**与 CI 对齐** → 规则里的命令应和 workflow 一致，避免「规则说 npm test，CI 用 pnpm」。

## 七、示例：最小可用 AGENTS.md

一个新仓库可以从六行开始，再长 gradual：

```markdown
# AGENTS
- 语言：中文沟通，commit 英文
- 测试：`npm test`
- 构建：`npm run build`
- 不改 dist/ 与 lockfile，除非任务明确要求
- 小步 PR，改完列测试命令
```

上面代码中，每一行都可**违反即错**，比「请保持代码质量」有用得多。项目长大后再拆章节，不要第一天写满十页。

## 八、小结

规则文件是仓库的「开卷考试封面」：写命令、写边界、写禁止，不写百科全书。短、硬、可验证，模型才真的 Ground 在你们的工程习惯上；剩下的细节交给 `@` 和源码。和 Grounding 文档一样，规则也要版本意识——过期规则比没有更糟，定期删改和写代码同等重要。
