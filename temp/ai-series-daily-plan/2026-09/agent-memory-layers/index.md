Agent 记忆（Memory）在工程里很少只是「一个向量库」这么简单。至少要分两层：**会话内**（当前对话窗口里的消息与工具观察）和**长期存储**（跨会话仍可检索的用户偏好、事实、任务状态）。

全塞进上下文会爆 token；全扔向量库又难保证「刚说过的话」立刻可用。分层的目的，是让每一类信息去它该去的地方。

下面是我整理的记忆分层：各层存什么、怎么读写、与会话摘要怎么配合。

很多人把「向量库里搜历史聊天」当记忆，结果召回的是噪声片段而非稳定偏好。记忆层要先回答「这条信息一年后还要不要、要不要精确定位」，再决定进 window、summary 还是 long-term。

![Agent 记忆分层示意](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/memory-layers_Gms_Aps7CQ.png)

## 一、先说一个具体麻烦

用户周一说：「以后报告默认用 PDF，别发 Word。」周三再来：「把上次的销售报告再发我一份。」

Agent 周三仍发 Word，且问「您偏好哪种格式？」——**长期偏好没写入持久层**；周一的对话又被新会话截断。用户觉得 Agent「没记性」，其实是记忆架构缺层。

另一类典型失败：把整段闲聊摘要写进长期记忆，下次检索「报告格式」却召出一堆无关寒暄，反而污染 RAG。

## 二、三层常用划分

（1）**工作记忆（上下文窗口）**  
当前 turn 的用户输入、系统提示、最近若干轮对话、本轮 Plan-Act-Observe 的观察。生命周期：本会话、受 token 上限约束。  
（2）**会话摘要（Session Summary）**  
会话变长时，由模型或规则把早期轮次压成短摘要，仍挂在会话 ID 下。生命周期：单次会话或短期缓存。  
（3）**长期存储（Long-term Store）**  
用户偏好、项目事实、未完成工单、授权范围等。生命周期：跨会话；读写靠结构化 API 或 RAG，而非整段聊天灌入。

![会话内与长期存储对比](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/session-vs-longterm_gtPAa3-ByZ.png)

## 三、什么该进长期存储

不是所有聊天都值得永久记住。较稳的写入触发：

（1）用户显式说「记住……」  
（2）宿主判定为**偏好或配置**（语言、格式、时区）  
（3）多步任务的**检查点**（已完成步骤、待确认项）  
（4）经用户确认的事实（避免把模型推测写进长期记忆）

写入时带 `source`、`updated_at`、`confidence`，便于后续 Grounding 与纠错。检索策略见系列第八篇 RAG 入门。

## 四、读写接口示例

长期记忆宜用键值或小型文档，而不是把记忆当聊天继续 append。

```json
{
  "user_id": "u-1001",
  "memories": [
    {
      "key": "report_format",
      "value": "pdf",
      "source": "explicit_user_2026-09-01",
      "updated_at": "2026-09-01T10:00:00Z"
    }
  ]
}
```

会话开始时，宿主把相关 memory **注入系统区或首条 user 块**，而不是等模型自己去「回忆」。上面代码中，`key` 应稳定，避免同一偏好多条冲突记录。

会话内若用户临时改口「这次例外用 Word」，只写进当前 session 即可，不要覆盖长期 `report_format`，除非用户明确说「以后都改」。

## 五、与会话摘要的配合

摘要不是长期记忆。它解决「上下文太长」时的压缩，见系列第二篇；**不能替代**「用户偏好 PDF」这类跨会话事实。

推荐顺序：先查长期 storage 取与本任务相关的键 → 再拼最近 N 轮原文 → 更早的用 session summary。Observe 里的工具大结果应截断进摘要，不要原样进长期层。

写入长期层前可加一道轻量规则：是否用户原话、是否可结构化、是否影响后续默认行为——三条里至少中两条再持久化。

删除记忆同样重要：用户说「别再记住报告格式」时，应支持显式 forget，并在 Observe 里确认已删，避免阴魂不散的默认值。

## 六、常见误区

（1）**向量库当唯一记忆**  
语义检索会 miss 精确配置项；偏好类宜键值 + 检索并存。  
（2）**自动写入模型推断**  
「用户好像是财务」写进长期，后续全偏了。  
（3）**不删不改**  
用户改主意后旧 memory 仍在，需版本或覆盖策略。  
（4）**长期记忆无权限**  
多租户项目里，memory 必须跟 `user_id` / `workspace_id` 绑定。  
（5）**子 Agent 各写一份**  
系列第六篇的协调者应统一 memory 写入点。

长期 memory 与 GDPR/注销也要挂钩：用户删号时，偏好与任务状态应可一并 purge，别留幽灵默认值。

调试记忆问题时，先在日志里标记「本条来自 window / summary / long-term 哪一层」，比笼统说「Agent 没记住」更快定位。

## 七、小结与系列导航

记忆分层的本质：**热数据在窗口，温数据在摘要，冷而重要的进长期存储**。写对层，RAG 与 Grounding 才有的放矢；否则检索到的全是聊天噪声。新会话开头用三行 memory 注入，通常比让模型自己「回忆」可靠得多。
