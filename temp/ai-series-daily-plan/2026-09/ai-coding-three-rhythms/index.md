用 AI 写代码，编辑器里其实有三种节奏：**Tab 补全**、**行内编辑（Inline Edit）**、**Agent 对话**。它们不是「哪个更强」，而是**改动范围**不同——从一行补全，到一块选中修改，再到跨文件执行任务。

很多人把三档混用：改一行却开 Agent，或跨十个文件还在 Tab 里硬补。结果是上下文浪费、改动难 review、测试漏跑。和 Agent 工程里的 Grounding 一样——**先给对的材料，再选对的工具**（见系列「Agent 工程笔记⑨：Grounding」）。

三种节奏的差异，本质是**你愿意让模型看多大范围、动多少文件**。范围越小，反馈越快，适合高频迭代；范围越大，闭环能力越强，适合探索与批量修改。选错档位的隐性成本，往往比多打几个字说明还高——Agent 一轮下来改错文件，撤回比重写更费时间。

下面是我日常用的切换规则与反例。

![Tab 补全、行内编辑与 Agent 的改动范围对比](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/three-rhythms-scope_pIi2BId1X.png)

## 一、三种节奏各自管什么

**Tab 补全**：你打字，模型猜下一行或下一小段。适合命名、样板代码、已知模式的延续。你几乎不用解释上下文——光标附近就是证据。它的局限也在这里：看不见其他文件的 import，也不知道测试怎么写。

**行内编辑**：选中一段，用自然语言说「改成 async」「加空值判断」。适合**单文件、局部、可目视 diff** 的改动。改完立刻扫一眼，成本最低。我把它当成「带 AI 的多光标」。

**Agent 对话**：跨文件搜索、跑命令、拆任务、写测试。适合**多步、多文件、需要探索** 的工作。代价是上下文长、输出面大，必须配合 review 和验收命令。我会把 Agent 当成「带读写仓库权限的实习生」：能干活，但要有任务卡和检查点。

## 二、一张切换表

![三种节奏切换决策](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/three-rhythms-switch_mT2peMUuT.png)

我按下面四条自问：

（1）只动当前光标附近几行吗？→ Tab  
（2）只动一个函数 / 一个块，且文件已打开？→ 行内编辑  
（3）要改 2 个以上文件，或要先找再改？→ Agent  
（4）要跑测试 / 安装依赖 / 读目录？→ 只能 Agent

再加两条经验：**不确定改哪** 时先 Agent 探索，定位后再收窄到行内编辑；**已经知道改法** 时别开 Agent，避免它「帮忙」改多余文件。

## 三、行内编辑示例

选中函数后，我会给**约束型**指令，而不是「优化一下」。

```text
把 fetchUser 改成 async/await，保留原有错误类型；
不要改函数签名和导出方式。
```

上面代码中，「保留错误类型」防止模型顺手换成 `throw new Error`；「不要改签名」把 diff 锁在实现层。

若改动涉及类型，我会同时选中类型别名那一段，或 `@` 类型文件，避免行内编辑只改实现、留下类型不一致。

## 四、该上 Agent 时的写法

跨文件任务先写**验收句**，再让 Agent 动手：

```text
目标：把 utils/date.ts 的 formatDate 抽到 lib/date/format.ts。
约束：所有 import 路径用 @/lib/date/format；跑 npm test 必须通过。
完成：列出改动文件清单。
```

这和 Grounding 思路一致：目标、边界、可验证出口写清楚，模型才不容易「看起来改完了其实漏文件」。

Agent 任务我会拆成「搜索 → 修改 → 验证」三步口述，而不是一条模糊的大目标。

## 五、和上下文的关系

Tab 几乎不占额外上下文；行内编辑只吃选中区 + 当前文件邻近；Agent 会吞规则文件、历史、`@` 引用。对话变长后，我会**新开 thread** 做下一阶段，而不是在同一条里从探索滚到大规模重构。

系列第四篇讲 `@` 引用策略；本篇只强调：**范围越大，越要控证据量**。

## 六、常见误区

（1）**小改用 Agent**：上下文塞满历史，反而慢。  
（2）**大改用 Tab**：补全没有全局视图，容易漏 import。  
（3）**行内编辑不选中范围**：模型不知道改哪，会动整文件。  
（4）**Agent 不设停止条件**：应要求「改完列文件清单 + 测试命令」。  
（5）**Tab 连续 accept 不读**：补全也会引入 subtle bug，关键路径仍要扫 diff。

## 七、一天里的组合用法

我典型的一天是这样组合的：上午写新功能，Tab 补全样板；下午修 bug，行内编辑改函数；傍晚做跨模块迁移，才开 Agent 跑测试。切换本身也有成本——开 Agent 要等索引、读规则，所以**不要为炫技而用 Agent**。

若团队结对，可以约定：探索阶段共享 Agent thread 结论，落地阶段各自行内改，避免同一文件两人各开 Agent 互相覆盖。

## 八、小结

三种节奏是**范围递增**的工具，不是能力排名。Tab 保流速，行内编辑保可控 diff，Agent 保跨文件闭环。切换的准则是：**改动范围有多大，就用多大的锤子**；探索用 Agent，落地用行内，流水用 Tab。记住 Grounding：范围越大，越要写清边界与验收。
