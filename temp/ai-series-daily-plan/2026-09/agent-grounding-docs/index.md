Grounding（接地）在 Agent 工程里，指的是：**让模型回答有据可查，且证据来自你提供的文档**，而不是靠训练记忆「编一个像真的」。

RAG 解决「找得到哪几段」；Grounding 解决「找到了之后，回答是否真的贴着这几段写」。两篇连着看，一条是检索，一条是约束生成。

下面是我整理的 Grounding 最小做法：从流水线到提示、输出格式与常见坑。

![未 Grounding 与已 Grounding 的对比](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/grounding-contrast_xXmoJuCEcX.png)

## 一、先说一个具体麻烦

你做了一个「问内部文档」的 Agent。用户问：「试用期多久？能否远程？」

模型答得很流利：「试用期三个月，支持混合办公。」听起来像 HR 手册。

你去核对原文，手册里写的是「试用期六个月，远程需主管审批」。检索其实没命中正确段落，模型却用常识补全了。

这就是**未 Grounding**：回答流畅，但不可信。比直接说「文档里没写」更危险。

## 二、Grounding 在工程里指什么

简单说，Grounding 不是多装一个向量库，而是一套**生成约束**：

（1）回答前，先把相关文档片段放进上下文（常靠 RAG，见系列第八篇「RAG 入门」）  
（2）生成时，明确要求「只依据给定片段；没有就拒答」  
（3）输出时，带上可核对的引用（文档 ID、段落、页码等）  
（4）必要时，再做一步核对：结论是否被片段支撑

可以把它想成写开卷考试：允许翻书，但**不许凭印象瞎写**；书上没有，就空着。

## 三、最小流水线

一条可落地的顺序如下。

（A）**检索**：按用户问题取 top-k 片段（关键词、向量或混合）  
（B）**装入上下文**：片段 + 元数据（来源、版本、更新时间）  
（C）**约束生成**：系统提示 + 低温度 + 结构化输出  
（D）**核对**：空检索拒答；有检索则抽查引用是否真在片段里  
（E）**输出**：正文 + 引用列表；无法支撑则降级为「未找到」

![Grounding 最小流水线](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/grounding-pipeline_C6zR3R50e.png)

检索为空时，不要默认让模型「尽量帮用户」。工程上更稳的路径是：返回固定拒答模板，或转人工。

## 四、三条硬约束（比形容词有用）

### 4.1 系统提示：写清边界

下面是一段可直接改写的系统提示骨架。

```text
你是内部文档助手。只能依据「本次提供的文档片段」回答。

规则：
1. 片段中找不到依据时，回答「文档中未找到相关信息」，不要猜测。
2. 每个事实句末尾标注引用，格式 [doc_id:chunk_id]。
3. 片段互相矛盾时，列出矛盾并说明无法确定，不要自行合并。
4. 不要引用片段以外的常识、旧版本记忆或联网知识。
```

上面代码中，第 1 条给出**拒答出口**；第 2 条把「贴文档」变成可检查的格式；第 4 条切断模型用参数化知识（parametric knowledge）补洞的习惯。

### 4.2 结构化输出：答案与证据分开

自由散文很难验收。更利于 Grounding 的是把「结论」和「引用」拆开。

```json
{
  "answer": "试用期为六个月；远程办公需主管审批。",
  "citations": [
    { "doc_id": "hr-handbook-2026", "chunk_id": "c-42", "quote": "试用期六个月" },
    { "doc_id": "hr-handbook-2026", "chunk_id": "c-87", "quote": "远程需主管书面审批" }
  ],
  "confidence": "grounded",
  "missing": []
}
```

上面代码中，`citations` 让宿主或评测脚本可以**逐条对原文**；`confidence` 与 `missing` 便于空检索或部分命中时分流，而不是一律输出长文。

检索为空时，期望形态类似：

```json
{
  "answer": "文档中未找到相关信息。",
  "citations": [],
  "confidence": "ungrounded",
  "missing": ["试用期时长", "远程办公政策"]
}
```

### 4.3 生成参数与上下文摆放

事实型问答，温度宜偏低（例如 0～0.3），减少「润色时改事实」。

片段建议放在用户问题**之前**，并在用户消息里重复一句：「仅依据以上片段」。文档版本、生效日期写在片段元数据里，避免模型用到旧 chunk 却按新口径回答。

## 五、和 RAG、上下文裁剪的关系

Grounding 吃检索质量。切块太大，噪声多，模型容易抓错句；切块太小，语义断掉，检索 miss 后更容易瞎编。切块策略见系列第八篇「RAG 入门」。

上下文太长时，「证据层」会被挤掉或混进摘要里，Grounding 也会变差。裁剪时要**优先保留当前问题的检索片段与验收规则**，而不是先删引用。相关思路见系列第二篇「上下文太长——砍什么、留什么」。

## 六、常见误区

（1）**只做了 RAG，没做拒答**  
检索 miss 仍让模型回答，等于未 Grounding。  
（2）**引用格式有了，但不验 quote**  
模型会编造 `[doc:99]`。宿主应检查 chunk 是否包含 quote 或语义等价句。  
（3）**文档过期未标记**  
索引里是 2024 版，用户以为是最新。元数据要有版本与更新时间。  
（4）**一次塞入整本 PDF**  
窗口浪费且焦点模糊；应检索后只装命中片段。  
（5）**把 Grounding 当成「多写请依据文档」**  
没有结构化输出与拒答路径，形容词挡不住补全冲动。

## 七、小结与系列导航

Grounding 的本质：**生成阶段把模型锁在给定证据上**，并用引用与核对让锁可验证。检索负责找材料；Grounding 负责用对材料、用足边界、找不到就停。
