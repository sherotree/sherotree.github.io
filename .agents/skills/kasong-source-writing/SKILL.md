# 卡颂「技术揭秘」源码写作

基于 [React技术揭秘](https://react.iamkasong.com/) 全文结构与典型章节提炼的**写作手法**（非冒充本人、不复制原文）。

语料与章节地图见 [corpus.md](corpus.md)。结构模板见 [examples.md](examples.md)。

## 硬约束

1. **只学风格，不抄内容**：不复述其原文段落、Demo 编号话术、独特类比原句、章节原句。
2. **不冒充**：不用「魔术师卡颂」「大家好我卡颂」署名；不暗示作者身份。
3. **事实自担**：源码路径、API、版本行为必须可核验；跟错版本就标明版本边界。
4. **观点有出处**：框架「为什么这样设计」优先引用官方/核心成员公开材料；个人推断要标明是推断。
5. **软广克制**：可保留 0～1 处自然延伸（Demo / 纠错 / 延伸阅读）；禁止照搬公众号口令领 Demo 话术。

## 全书方法论（先定坐标系，再写一章）

宗旨一句话：**严谨、易懂的源码分析教程**。

行文三条（可写进前言，也可当自检）：

1. **不预设观点** —— 设计动机尽量来自官方/核心团队公开分享，而非作者站队。
2. **参考资料丰富** —— 文末给文章/演讲/源码锚点；关键路径链到源码或图。
3. **版本可追踪** —— 标明分析基于的版本；重大重构用「注意」框标出。

### 自顶向下（全书骨架，禁止反着写）

```text
理念（要解决什么问题）
  → 架构（模块如何分工）
    → 实现（算法/数据结构）
      → 具体代码（函数体与字段）
```

**故意不从**日常 API（`render` / `setState` / 某个 Hook）开篇。先讲清「为什么需要异步可中断」再进 Fiber，再进 `beginWork`。直接贴 API 源码 → 读者会掉进汪洋大海。

全书可分三篇（可裁剪，但抽象递减顺序不要乱）：

| 篇 | 读者带走什么 | 典型内容 |
|----|--------------|----------|
| **理念篇** | 问题、瓶颈、心智模型 | CPU/IO 瓶颈、时间切片、新旧架构对比 |
| **架构篇** | 阶段与模块边界 | render/commit、递与归、双缓存 |
| **实现篇** | 算法与数据结构细节 | Diff、Update、Hooks、Scheduler |

单章内部同样递减：概念定义 → 分类/二分 → 精简代码 → 边界注意 → 下节钩子。

## 单章结构 DNA

固定节奏（可略删，勿打乱）：

```text
1. 承接上节（一句话回顾 + 本节要回答的问题）
2. 提出问题（因何而来？做什么？和 X 什么关系？）
3. 分层定义 / 二分法（三层含义、mount vs update、递 vs 归…）
4. 机制拆解（每节只推进一个判断）
5. 精简源码 + 注释分类（大段用 // ...省略）
6. 例子走读（组件 → 树 / 调用序列）
7. 「注意」框（易混点、版本坑、性能取舍）
8. 总结 + 抛出下一问
9. 参考资料
```

### 标题

- 对象清晰：`Fiber的起源` / `方法概览` / `mount 时` / `Diff的瓶颈以及React如何应对`
- 可用「什么是 X」「从传参看方法执行」这类**认知脚手架标题**
- 不用悬念营销式标题（预测/反常识/焦虑钩子）

### 开篇衔接句式（自创内容，学节奏）

- `通过上一节的学习，我们了解了…`
- `上一节我们了解到…可以分为…。这一节我们看看…究竟做了什么。`
- `接下来让我们了解下…因何而来？他的作用是什么？`
- `我们现在还不需要学习这两个方法，只需要知道…`

### 收尾

- 用 1～3 句收回本节结论
- **必须留钩子**：`那么…呢？我们会在下一节讲解。`
- 参考资料：演讲名、官方文档、关键源码文件；中英文皆可

## 文风 DNA（必须遵守）

### 1. 段落与语气

- 一段一事；多数段落 **1～3 句**
- 教师带读感：用「我们」，少用「笔者以为」
- 口语但不煽情：`像蚂蚁搬家一样`、`答案十分巧妙` —— **类比必须自创**
- 技术名用行内代码：`` `Fiber` ``、`` `beginWork` ``、`` `current === null` ``
- 中英文之间加空格；全角中文标点；引号优先 `「」`
- 常用衔接：`我们知道`、`基于此`、`值得一提的是`、`那么…如何…呢？`、`可以看到`、`简单来说`（慎用，源码文更常用「从代码可以看出」）

### 2. 解释手法（本 skill 核心）

| 手法 | 用法 |
|------|------|
| **问题 → 瓶颈 → 解法** | 先问制约因素（CPU/IO），再落到机制（时间切片 / Suspense） |
| **新旧对比** | 递归不可中断 vs 异步可中断；stack vs Fiber |
| **多层含义** | 一词多义时显式拆层（架构 / 静态数据结构 / 动态工作单元） |
| **二分主轴** | `mount`/`update`、`current === null?`、同步/并发 workLoop、单节点/多节点 Diff |
| **从传参看执行** | 先列参数语义，再推分支，再进函数体 |
| **递归心智模型** | 先给「递归版」帮助理解，再说明真实实现是可中断遍历 |
| **思想实验** | 「假设也给每个节点打 Placement，会怎样？」→ 引出真实优化 |
| **延迟讲解** | 优先级、Scheduler 等：「会在讲解 X 时再介绍」，避免一章塞爆 |
| **身份切换** | 框架使用者看设计动机够用；讲源码架构时切换到框架开发者视角 |
| **官方锚定** | 理念/动机链到官网、Conf 演讲、RFC/PR |

顺序永远是：

```text
场景或上节结论 → 问题 → 分类框架 → 机制 → 精简代码 → 例子 → 边界
```

坏顺序：先甩 500 行函数体，再补故事。

### 3. 代码规范

- 块前一句说明意图：`其中传参：` / `举个例子，如下的组件结构：`
- **只留骨架**：大段逻辑写 `// ...省略`；注释按「含义分类」分组，而不是逐行翻译
- 关键字段旁注「何时用」：`会在后续的更新流程中使用到具体属性时再详细介绍`
- 需要证明调用序时，用编号步骤列表（`1. root beginWork` …）或极简递归伪代码
- 禁止为充字数贴完整生产源码

### 4. 「注意」框与 Demo

- **注意**：版本重构、命名易混（`return` 不是 parent）、特殊优化（单一文本子节点）、和直觉相反的行为
- Demo：能小则小；说明「在什么时机打印什么」；读者应能自己跟一遍调用序
- 选读章开篇标明：`本章为选读` + 对后续有无依赖

### 5. 图与示意

- 树结构、双缓存左右对比、调用序：优先简图或 Mermaid；图服务于「走读」
- 不为配图而配图；不配情绪图、梗图

## 工作流

```text
- [ ] 本章在全书中的抽象层级是否对（理念/架构/实现）
- [ ] 开篇是否承接上节并抛出本节问题
- [ ] 是否先给分类/二分，再进代码
- [ ] 源码是否骨架化 + 注释按含义分组
- [ ] 是否有走读例子（组件 → 树 / 调用序列）
- [ ] 易混点是否进「注意」；未讲完的是否「下节再讲」
- [ ] 总结是否收回结论并钩住下一章
- [ ] 参考资料是否可点；无冒充、无抄原文
```

## 适用 / 不适用

**适用**：框架/运行时源码系列、Reconciler/调度/Diff/Hooks 原理文、技术揭秘体电子书章节  

**不适用**：Changelog 翻译、纯 API 手册、行业评论/热点观点文、需要严格学术引用的论文体
