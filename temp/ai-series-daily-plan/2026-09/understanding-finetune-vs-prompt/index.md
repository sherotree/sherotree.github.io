想让模型按你的口径说话，有两条路：**改权重（Fine-tuning）**，或**改输入（Prompt Engineering）**。前者动模型本身，后者动每次请求的上下文。

两者都能「定制行为」，但成本、持久性和适用场景差很多。选错路，要么烧钱训练，要么 Prompt 越堆越长。

下面是我整理的对比：各自改什么、什么时候用哪条。

![Fine-tuning 改权重 vs Prompt 改输入](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/finetune-vs-prompt-contrast_NBl8m-jj5.png)

## 一、先说一个具体麻烦

你要做一个客服机器人，必须按公司话术回复，禁止承诺未上线的功能。

试了几版 Prompt，模型大多数时候遵守，但偶尔「创意发挥」——把 beta 功能说成了已上线。你会想：要不要 Fine-tune 一个专用模型？

## 二、Prompt 在改什么

Prompt 不改模型参数，只在每次请求里**注入指令、示例、文档**。效果随上下文窗口大小而有限——窗口满了，旧指令可能被挤掉。

适合：

（1）规则经常变、不想重新训练  
（2）需要引用最新文档（配合 RAG）  
（3）团队小、没有 GPU 训练资源  
（4）快速试错，今天改明天生效

局限：模型底层习惯仍在，复杂约束要靠长 Prompt 或结构化输出硬压，token 成本高。

## 三、Fine-tuning 在改什么

Fine-tuning（微调）在基座模型权重上继续训练，用你提供的输入-输出对（或偏好数据）**调整参数**。改完后，行为写进权重，推理时不必每次重复大段指令。

![Fine-tuning 持久改权重，Prompt 临时注入上下文](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/finetune-prompt-mechanism_y9f81Gm0x.png)

常见形态：

（1）**全量微调**——改全部参数，效果最好，成本最高  
（2）**LoRA / QLoRA**——只训练低秩适配器，省显存，主流做法  
（3）**偏好对齐（DPO 等）**——让输出更符合人类偏好，而非单纯模仿样本

适合：固定风格、固定格式、高频重复任务，且有一批高质量训练数据。

### 3.1 数据从哪来

微调样本常见格式是「用户消息 → 理想助手回复」。客服场景可脱敏历史工单；代码场景可收 PR 里「问题描述 → 合格补丁」。**几百条干净数据**往往比几万条噪声更有用。偏好对齐（DPO）还需要「更好 / 更差」成对样本，成本更高。

## 四、一张对比表

| 维度 | Prompt | Fine-tuning |
| --- | --- | --- |
| 改什么 | 输入上下文 | 模型权重 |
| 成本 | 按 token 付推理费 | 训练费 + 推理费 |
| 更新速度 | 改文本即生效 | 需重新训练 |
| 知识时效 | 可接 RAG 喂新文档 | 权重里的知识会过时 |
| 数据需求 | 几条示例即可试 | 通常要数百条以上高质量样本 |

## 五、决策顺序（实用）

我通常按这个顺序想：

（1）**先 Prompt + 结构化输出**—— JSON Schema、函数调用，Often 够用。  
（2）**再加 RAG**—— 知识类问题先补检索，比微调便宜。  
（3）**仍不够才 Fine-tune**—— 格式极固定、调用量极大、Prompt 已塞满窗口。

合规场景（必须固定拒答话术、禁止某些承诺）有时值得微调，因为 Prompt 再长也可能被越狱或长上下文稀释。此时微调 + RAG + Grounding 三板斧一起上，比单押 Prompt 更稳。

也有中间路线：**Prompt 缓存**（重复系统提示只算一次）和 **Few-shot in context**，介于两者之间。OpenAI 等厂商的 `prompt caching` 对长系统提示按缓存 token 低价计费——适合规则稳定、调用频繁的场景，但知识更新仍靠 RAG，不靠缓存。

## 六、常见误区

（1）**微调不能替代 RAG**—— 权重里的知识有截止日期，私有文档仍要检索。  
（2）**微调数据质量 > 数量**—— 脏数据会把坏习惯写进权重。  
（3）**不是 Prompt 失败就微调**—— 很多是检索、Grounding、验收没做好。  
（4）**微调后仍要 RAG**—— 权重里的世界知识不会因为你微调了客服话术就自动更新。

## 七、小结

Prompt 改输入，临时、灵活、适合变规则；Fine-tuning 改权重，持久、适合固定行为与高调用量。先 Prompt 和 RAG，确认瓶颈后再考虑训练——这是更省钱的默认路径。

微调上线后还要做版本管理与回滚：权重是 artifact，Prompt 是文本，运维流程不同。别把微调模型当成「一劳永逸」——数据漂移、政策变更仍会逼你重训或退回 Prompt+RAG 组合。

小团队若没有标注资源，**Prompt + 示例 + RAG** 往往已经覆盖八成场景。Fine-tune 的门槛不在 GPU，而在持续维护一份干净、代表真实分布的数据集。

OpenAI、Anthropic 等也提供「轻量微调」或偏好对齐 API，按 token 训练计费。决策时把**训练 token 费 + 后续推理单价 + 运维人力**一起算，Often 会发现 Prompt 缓存 + RAG 更划算——除非调用量已经把 Prompt 成本撑爆。

还有一个中间层：**系统提示 + 工具定义** 其实也在「改输入」，但比每次手写 user message 更稳定。把不变的部分沉到 system / tools，把变的部分留给 user，Often 能延迟 Fine-tune 到来的时间点。这是工程上最常被低估的一层「软微调」。
