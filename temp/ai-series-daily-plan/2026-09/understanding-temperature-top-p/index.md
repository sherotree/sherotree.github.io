大模型生成文本时，每一步都会在词表上算出一组概率，再**抽样**出下一个 token。Temperature 和 Top-p 就是控制「抽多随机、抽多保守」的两个旋钮。

同样的问题问两遍，回答不完全一样——随机性就从这里来。搞清机制，才知道什么时候该开、什么时候该关。

下面是我整理的采样参数要点：它们怎么改概率分布，以及各适合什么任务。

![Temperature 改变概率分布形状：高温更平、低温更尖](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/temperature-distribution_YbeAYNoBC.png)

## 一、生成不是「选最高分」

模型每步输出的是 logits，经 Softmax 变成概率分布。如果永远选概率最高的 token（greedy），回答会死板、重复。

实际用的是**随机采样**：按概率抽签。概率 0.6 的词，大约六成机会被选中。Temperature 和 Top-p 在抽签之前改这张「彩票」。

## 二、Temperature 在干什么

Temperature（温度）记作 T，在 Softmax 之前把 logits 除以 T：

```python
# 示意：logits [2.0, 1.0, 0.1]，不同 T 的效果
# T=1.0  → 正常分布
# T=0.2  → 高分更高、低分更低，几乎总选第一个
# T=1.5  → 分布更平，冷门词更容易被抽到
```

上面代码中，**T 越低越确定，T 越高越随机**。事实型问答常用 0～0.3；创意写作可试 0.7～1.0。T 接近 0 时近似 greedy。

## 三、Top-p（Nucleus Sampling）在干什么

Top-p 不看温度，而是**截断长尾**：按概率从高到低累加，直到总和达到 p（例如 0.9），只在这批候选里重新归一化并抽样，其余低概率 token 直接丢掉。

![Top-p 核采样：只保留高概率候选](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/top-p-nucleus_O0TCxdgDj.png)

p=0.9 表示「最可能的那些词加起来占 90% 概率 mass」的集合作为候选池。模型很确定时池子小，不确定时池子大——比固定只取 top-k 更自适应。

API 里常见写法：

```json
{
  "temperature": 0.7,
  "top_p": 0.9
}
```

上面代码中，两者可同时设。一般建议**只调一个**：同时拉低 temperature 又压低 top_p，容易过度保守。

### 3.1 seed 与可复现

部分 API 支持 `seed` 固定随机源。temperature=0 且设 seed，同样输入可得到同样输出——适合回归测试。创意场景不要强求逐字 reproducible；测试 JSON 解析与工具调用时，低温 + seed 更省心。

## 四、和 Top-k 采样对比

Top-k 固定只保留概率最高的 k 个 token（例如 k=40），再在这 40 个里抽样。问题是：模型很确定时，可能 top-5 就占了 99% 概率，硬留 40 个反而放进一堆几乎不可能的词；模型不确定时，40 个又可能不够。

Top-p 按**累积概率 mass** 动态决定池子大小——确定时池子小，不确定时池子大，通常比固定 k 更合理。两者也可与 Temperature 组合，但实践中建议主调一个参数，避免「又冷又窄」导致输出重复。

## 五、怎么选参数

| 场景 | Temperature | Top-p | 说明 |
| --- | --- | --- | --- |
| 代码生成 / JSON | 0～0.2 | 0.9 或默认 | 要低随机，格式才稳 |
| 事实问答 | 0～0.3 | 0.9 | 减少胡编 |
| 头脑风暴 | 0.8～1.0 | 0.95 | 允许发散 |
| 需要可复现 | 0 | — | 配合固定 seed（若 API 支持） |

Grounding 与结构化 JSON 输出宜低温；头脑风暴、文案多版本可高温。若发现输出总在几个词里打转，先略升 temperature 或略放宽 top_p，而不是一味加长 Prompt。

API 文档里的 `top_k` 是另一个旋钮：只保留概率最高的 k 个 token 再抽样。与 top_p 类似但更简单；三者（temperature / top_p / top_k）同时拧死，容易得到重复、干瘪的文本——**先默认值，再单变量微调**是更省时间的调参法。

## 六、常见误区

（1）**temperature=0 不是「无随机」的万能解**——部分实现仍可能有微小浮动。  
（2）**高温度不能弥补模型不懂**——只会更胡编，不会更懂。  
（3）**Top-p 和 Top-k 别混**——Top-k 固定取前 k 个，Top-p 按概率 mass 动态截断。

## 七、小结

随机性来自按概率抽样。Temperature 拉平或拉尖分布，Top-p 砍掉低概率尾巴。事实任务低温，创意任务高温；两者通常择一微调即可。

别把采样参数当成「模型智商旋钮」——它们只改抽签方式，不改模型知识边界。要减少胡编，靠 RAG、Grounding 与拒答；要增加文采，再动 temperature。

生产环境建议把 temperature / top_p 写进配置而非散落在代码魔法数里。事实型流水线默认低温；同一服务若兼做创意与问答，最好**分路由或分模型**，而不是一套参数硬扛全部场景。

流式输出（streaming）不改变采样逻辑，只是每出一个 token 就推给客户端——用户感觉「字在蹦」，底层仍是逐步 softmax + 抽样。调试采样问题时，可先关 streaming、固定 seed，便于对比两次输出是否一致。

部分厂商还提供 `frequency_penalty` / `presence_penalty`，用来抑制重复用词——与 temperature 不同，它们直接改 logits 而非分布形状。写长文若出现循环套话，可略调 penalty；写 JSON 则通常保持默认，避免破坏格式 token。采样参数是一组杠杆，别只拧其中一根。记住：**随机性服务于任务目标**——要稳则冷，要活则热，要多样则略开 top_p，而不是反过来用参数弥补模型不该答的问题。
