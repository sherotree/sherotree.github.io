IDE 里 `@` 引用，本质是给模型**手动 Grounding**：你指定「这次回答必须看着这些文件」。引对了，回答贴代码；引错了或引太多，窗口被噪声占满，和没 Grounding 一样危险。

Agent 工程笔记⑨讲生成要贴文档片段；在编辑器里，`@` 就是你选的片段来源。差别是：**检索是自动的，`@` 是你亲手点的证据**。系列第三篇的规则文件是固定层；本篇讲动态层怎么省、怎么准。

窗口不是无限的。引用的文件越多，留给模型推理和工具输出的空间越少，长对话里还会出现「前半段文件被挤掉」的现象。省上下文不是抠门，而是让**关键证据留在窗口里**——这和 Grounding 流水线里优先保留检索片段是同一逻辑。

下面是我的 `@` 引用策略。

![@file @folder 引用决策树](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/at-refs-tree_YUyVTu6QV.png)

## 一、四种 @ 怎么用

（1）**@file**：已知要改或要对齐的**单个文件**——接口定义、现有实现、测试样例。  
（2）**@folder**：需要模块全貌但文件不大——例如 `components/Button/`。  
（3）**@code / 符号**：只关心一个函数，避免整文件进上下文。  
（4）**@docs**：设计文档、ADRs，适合「按 spec 改」的任务。

原则：**能小不大，能文件不文件夹**。folder 引用前先看一眼目录大小，超过二十个文件就先让 Agent 列出候选再收窄。

## 二、上下文预算

![上下文窗口预算示意](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/at-refs-budget_vufSYa68L.png)

窗口里通常还有：规则文件、对话历史、模型自己的工具输出。我会预留顺序：

（1）规则与任务说明（约 10%）  
（2）**核心 @ 引用**（约 40%～50%）  
（3）历史与工具结果（其余）

引用超过 3 个大文件时，先问：能否只 `@` 类型定义 + 一个调用示例？能否用 `@code` 代替整文件？

对话超过十轮且任务已变，**新开 thread + 重新 @**，比带着旧历史更省 token。

## 三、任务模板示例

改 API 时，我固定 `@` 三样：

```text
@src/types/user.ts
@src/api/user.ts
@src/api/user.test.ts

任务：给 User 增加 timezone 字段，保持现有错误码风格。
```

上面代码中，类型、实现、测试**三角证据**，模型不容易漏改 schema 或断言。

重构时再加「**对照文件**」：旧实现与新 hook 各 `@` 一份，避免模型凭空发明 API。

## 四、该少 @ 的时候

（1）**Agent 能自己搜**且你不确定路径——先让它 `grep`，命中后再 `@` 确认。  
（2）**生成全新模块**——没有对齐对象， `@` 整个 `src/` 只会添乱。  
（3）**二进制、锁文件、生成物**——除非任务明确相关。  
（4）**巨大 JSON fixture**——贴片段或 `@` 小样本即可。

## 五、和自动索引的关系

Cursor 等会索引仓库，但索引不等于「本次必看」。Explicit `@` 提高**引用优先级**；Implicit 索引适合探索阶段。探索完记得**收窄 @**，否则下一轮仍带着旧噪声。这和 Grounding 流水线里「检索后只装命中片段」同构。

## 六、裁剪优先级

上下文不够时，我按顺序删：

（1）冗长对话历史（新开 thread 更好）  
（2）非核心的 `@folder`  
（3）工具输出的长 log（保留最后 50 行）  

**不删**：规则文件、当前任务的核心 `@file`、验收标准。

## 七、常见误区

（1）`@` 整个 monorepo 根目录。  
（2）只 `@` 要改的文件，不 `@` 测试——改完无法自证。  
（3）把 secrets 文件 `@` 进去——日志与泄漏风险。  
（4）同一文件既在规则里又在 `@` 里重复贴全文。

## 八、场景对照

| 任务 | 推荐引用 |
| --- | --- |
| 修单测失败 | `@` 测试 + 被测文件 + fixture |
| 对齐 REST 风格 | `@` 现有 handler + types |
| 读陌生模块 | 先 `@` README，再 `@` 单条主路径 |
| 写全新 CLI | 只 `@` 类似命令文件一个 |

这张表不是死规则，但能减少「 `@` 整个 src」的惯性。每次多 `@` 一个文件前，问：删掉它，模型还能答对吗？不能才加。

## 九、小结

`@` 是手动的、可审计的 Grounding。选 file 还是 folder，看证据粒度；控总量，看窗口预算。引少而准，比引多而全更贴代码。系列 Grounding 文里的「只装命中片段」，在 IDE 里就是你点的每一次 `@`。
