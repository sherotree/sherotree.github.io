# 阮一峰风格中文技术写作

基于其博客中长青、高传播技术文提炼的**写作手法**（非冒充本人、不复制原文）。

语料说明见 [corpus.md](corpus.md)。结构与图文示例见 [examples.md](examples.md)。

## 硬约束

1. **只学风格，不抄内容**：不复述其文章段落、类比原句、代码示例、配图或独特金句。
2. **不冒充**：不要用「阮一峰」「ruanyifeng」署名或暗示作者身份。
3. **事实自担**：步骤、命令、截图、结论必须来自用户题材与实测；不确定就标明不确定。
4. **原创优先**：同类主题用自己的场景、自己的工具页、自己的图与代码。
5. **图文代码默认要有**：技术文不是纯文字墙。该配图处须产出真实图片文件并嵌入；该示例处给代码块。缺图、假路径或「待补占位」视为未完成。

## 文风 DNA（必须遵守）

### 1. 标题

- 形态：`理解X` / `X入门` / `X详解` / `X初探` / `X教程` / `X的一个简单解释`
- 短、直、无营销腔；可含一个核心对象，不加「震惊」「必看」

### 2. 开篇（3～6 个短段）

固定顺序，可略删不可打乱逻辑：

1. **一句话定义**对象是什么、用来干什么
2. **为何现在重要**或为何难懂（材料抽象、术语多）
3. **本文承诺**：简明通俗地讲清什么；必要时说「下面是我的整理/笔记」
4. 不写悬念营销，不堆 emoji
5. 开篇后或第一节前，常可插入首图（见「配图」）

### 3. 结构骨架

主线优先：

`场景痛点 → 为什么需要 → 核心思路（可先类比）→ 分步拆解 → 细节/参数 → 误区或对比 → 收束`

章节用中文序号：

```text
## 一、……
## 二、……
### 2.1 ……
```

或旧式 `一、` `二、`（无 `#`）亦可，全文统一即可。

### 4. 段落与句子

- 一段一事；多数段落 **1～3 句**
- 优先短句；一句只推进一个意思
- 常用衔接：`简单说`、`所谓……指的是`、`下面……`、`不难看出`、`举例来说`、`上面代码中`
- 术语首次出现：`中文（English）`，随后可只用中文或英文之一
- 列举用 `（1）（2）（3）` 或短列表，不写空话 bullet

### 5. 解释手法（最重要）

抽象概念先给**生活类比或具体场景**，再给正式定义，再给机制。

- 好：先讲具体麻烦 → 再讲术语与机制
- 坏：先甩规范术语表再讲故事

类比必须**自创**，贴合当前题材；不要复用其博客里的原比喻（如小区门禁、云冲印等）。

流程超过三步时：文字列出（A）（B）（C）后，优先再配一张流程图或示意图。

### 6. 配图（其文常见，写文必须执行）

技术长文默认 **至少 2 张图**；工具教程默认 **至少 3 张**（上传/操作、结果、对比或界面之一）。纯概念短文可减至 1 张示意图，但须在文中说明为何无需更多图。

**写文时必须实际产出图片文件**（下载 / 截图 / 导出 / 生成），嵌入 Markdown。禁止用「待补占位」交差，尤其禁止对自己的工具页只写占位不截图。

#### 6.1 什么时候必须配图

| 场景                         | 配什么           | 获取路径（见 6.2）                           |
| ---------------------------- | ---------------- | -------------------------------------------- |
| 自己的工具页步骤             | 真实界面截图     | **A. 自动截图**（必须）                      |
| 多步骤流程 / 协议交互        | 流程图、时序示意 | **D. AI 手绘示意**（默认，见 6.5）           |
| 结构关系（模块、目录、架构） | 简图             | **D**                                        |
| 概念氛围 / 主题插图（非 UI） | 照片或插画       | **B. Unsplash / Pexels** → 不行再 **C/D**    |
| 前后对比（转换、优化）       | before / after   | 工具页用 **A**；否则 **D**                   |
| 第三方产品 UI（如 Cursor）   | 仅在可合法取得时 | 优先官方素材或自有环境截图；不要乱爬他人站点 |

#### 6.2 配图生成规则（按类型分流，写文时执行）

先判断这张图属于哪一类，再走对应流水线。

##### A. 自己的工具页截图（强制自动截，禁止占位）

适用于 uwarp / 本仓库托管工具、本地已跑起来的产品页。

1. 用浏览器自动化打开真实 URL（优先生产域，如 `https://www.uwarp.design/tools`；或本地 dev）。
2. 按文章步骤操作到对应状态（上传区、处理中、结果预览等）。
3. 截取关键区域或视口，保存到文章同级 `images/`。
4. 文件名可读：`potrace-upload.png`、`potrace-result.png`。
5. 立刻写入 Markdown 的 `![alt](./images/xxx.png)`，**不要**再写「上图是……」或「（图片说明：……）」。

失败时：换本地地址重试、缩小视口、去掉 cookie 墙后再截——**仍不得改成「待补截图」占位**。若环境实在无法打开页面，在回复里说明阻塞原因，并改用已有仓内截图资产；不要留假路径。

##### B. Unsplash / Pexels（主题插图、氛围图）

适用于：开篇主题图、抽象概念的视觉隐喻、与 UI 无关的配图。

1. 用英文关键词检索 Unsplash 或 Pexels（API 或官方站点均可）。
2. **合适才用**：画面与段落主题相关、构图干净、无大量无关文字、可商用许可清晰。
3. 下载到 `images/` 并嵌入正文。
4. 不合适（风格违和、太满、有水印、答非所问）→ 不要勉强下载，转入 **D**。

禁止：从百度图片、任意博客、商业官网批量爬图冒充配图。

##### C. Mermaid / 矢量草稿（禁止默认主题直接入稿）

**流程 / 架构 / 对比类示意图，默认不用 Mermaid 成品图。** Mermaid 仅可在本地快速理清结构；若导出 PNG，不得使用默认 `neutral` / 灰盒直箭头主题直接嵌入正文——与系列视觉不统一。

若因环境限制无法 AI 出图，才允许手写风 SVG；仍须满足 6.5，且不得呈扁平商务流程图观感。

##### D. AI 手绘示意图（流程 / 架构 / 对比的默认路径）

适用于：流程、时序、架构、对比、心智模型——**本仓库博客系列的统一风格**。

1. 用图像生成工具（如 Cursor `GenerateImage`）出图；**必须**指定手绘风（见 6.5）。
2. 优先传入系列风格锚点作参考（见 6.5「风格锚点」），保证纸感、铅笔线、中文标签一致。
3. 保存到文章同级 `images/`，文件名可读：`grounding-contrast.png`。
4. 发布稿上传 ImageKit（见 6.6），正文嵌入 CDN URL；囤稿阶段可暂用 `./images/...`。
5. **不要**用 AI 图假装「本工具真实界面」；真实 UI 只能走 **A**。
6. **禁止**用 Mermaid 默认导出、光滑扁平 PPT 风、紫蓝科技感堆料替代本路径。

##### 决策顺序（摘要）

```text
需要配图
  ├─ 自己的工具 UI / 操作步骤     → A 自动截图（必须成功嵌入）
  ├─ 流程 / 架构 / 时序 / 对比    → D AI 手绘示意（默认；见 6.5）
  │                                  └─ 仅草稿可用 Mermaid 理清结构，不得默认主题入稿
  └─ 主题插图 / 氛围 / 抽象隐喻   → B Unsplash/Pexels
                                      └─ 无合适 → D 手绘 AI 示意
```

#### 6.3 怎么写进 Markdown

只插入图片，正文继续讲主题；**不加图说、不解释「上图是什么」**。

```markdown
![上传 PNG 后的预览区](./images/potrace-upload.png)

打开页面后，上传图片。工具会在本地读取像素、跑 Potrace……
```

规则：

- 图片文件与 Markdown **同时交付**；囤稿用 `./images/...`，发布稿用 ImageKit CDN URL（见 6.6）
- `alt` 写清画面（无障碍与备份用），读者通常看不见
- **禁止**图下再写：`上图是……` / `下面这张图……` / `（图片说明：……）` / 图库署名或来源说明

#### 6.4 配图禁忌

- 不要「待补占位」、空 `images/` 假引用
- 不要用无关美女图、表情包、大段文字长截图充数
- 不要为配图单独加一段解说（图应自己够清楚，或由上下文自然承接）
- 不要爬取未授权站点图片
- 截图若含隐私/密钥，先打码
- 图库图不要冒充产品截图；AI 图不要冒充实机界面
- 示意图不要用 Mermaid 默认灰盒主题、光滑渐变、玻璃拟态、紫蓝科技感堆料
- 流程 / 架构类**必须**走 6.5 手绘风，与系列已有配图保持一致

#### 6.5 示意图视觉标准：手绘风（系列统一）

流程、架构、对比、心智模型类配图，**一律**采用本仓库已落地的**铅笔手绘风**，而不是 Mermaid 默认导出、扁平 UI 或商务 PPT 风。

**风格锚点（生成时作 reference，对齐用）：**

- Agent 工程笔记：`agent-tool-failure-three-layers` 配图（三层排查、纸感铅笔线）
- Grounding 对比 / 流水线：`grounding-contrast`、`grounding-pipeline`（双栏对比、编号步骤流）

**必须满足的特征：**

- 铅笔或炭笔描边，线条略不齐；米白 / 浅纸色底（如 `#faf7f2`），少渐变、无玻璃拟态
- 方框、箭头、分区用手绘圆角；中文标签像手写印刷体，短句、可读
- 可配简单手绘图标（大脑、文档、放大镜、对话气泡等），一图一个观点
- 横版为主，常用 `16:9`；信息量少，避免一图塞满术语表

**生成提示词要点（给 `GenerateImage` 等）：**

```text
Hand-drawn pencil sketch on textured off-white paper. Chinese labels in handwriting-style
print. Charcoal lines slightly wobbly. Warm paper texture. Sparse text. No purple gradients.
No glossy UI. No flat Mermaid flowchart look. Landscape 16:9.
```

**禁止：**

- Mermaid CLI 默认主题 PNG 直接入稿（灰盒 + 直箭头 + 系统 sans-serif）
- 与系列锚点图风格明显不一致的「换一套视觉语言」

适用：Crawl→Index→Rank、Tab/Inline/Agent 分层、Grounding 流水线、工具失败三层等。  
不适用：真实工具截图（仍走 A）、照片类氛围图（仍走 B）。

#### 6.6 博客配图发布：ImageKit

本仓库已发布文章的正文配图，统一走 ImageKit CDN（与 `agent-tool-failure-three-layers` 等稿一致）。

1. 手绘示意或截图落盘到文章 `images/`。
2. 用 `imagekit-upload` skill 上传：

```bash
python3 .agents/skills/imagekit-upload/scripts/upload.py \
  ./images/grounding-contrast.png /blog/2026/09 --compress --file-name grounding-contrast.png
```

3. 正文嵌入返回的 `url`（`https://ik.imagekit.io/4pjac7gmxh/...`），不要只留本地相对路径就当作发布完成。
4. 文件夹按文章 `date` 的年月：`/blog/{YYYY}/{MM}/`。
5. 博客大图默认加 `--compress`（`w-1600,h-1600,c-at_max,q-82`）。

### 7. 代码块（其文高频，按需出现）

不是每节都要代码；**读者需要照着做、或需要看见报文/配置长什么样时，必须给代码块**。

#### 7.1 什么时候必须给代码

| 场景                 | 示例类型                       |
| -------------------- | ------------------------------ |
| HTTP / 协议 / 头字段 | 最小请求或响应报文             |
| API / CLI / 配置     | 可复制的命令或片段             |
| 前端用法             | 最小 HTML/JS/CSS               |
| 对比两种写法         | 两段短代码，先错后对或先旧后新 |
| 仅概念、无操作       | 可以不给代码，改用列表或图     |

#### 7.2 写法固定节奏

顺序必须是：

1. 先用文字说明「接下来看一个例子 / 下面是……」
2. 再给 **短** 代码块（语言标记要写对：`bash` `html` `js` `http` `json` 等）
3. 块后立刻用「上面代码中……」点出 **1～3 个**关键点

```markdown
下面是一个最简单的例子。

\`\`\`html
<img src="logo.svg" alt="logo" width="120" height="120" />
\`\`\`

上面代码中，SVG 被当成普通图片引用。若要用 CSS 修改 \`fill\`，通常改为内联 SVG。
```

#### 7.3 代码块禁忌

- 先甩五十行再解释
- 把整份源文件贴进文里
- 无语言标记的裸 fence（除非纯文本报文且已说明）
- 代码与上下文脱节（读者不知道这段在证明什么）
- 能口述清楚的纯流程，不要硬凑无意义代码

### 8. 语气

- 可用第一人称「我」，像老师给同学讲，不装专家腔
- 可承认边界：「本文不涉及……」「我主要关注……」
- 不嘲讽读者；少用「众所周知」「显然」压人
- 禁用：小红书体、鸡汤金句堆砌、过度感叹号、营销 CTA 连发

### 9. 收尾

- 用一两段总结「它到底是什么 / 你现在可以做什么」
- 技术长文可用 `（完）`
- 若推广中文站工具：最多 **1 处**自然提及（「也可以用在线工具直接做」+ 具体工具页），不要硬广段

### 10. 排版（对齐其文档习惯）

- 中英文之间加空格：`使用 Cookie 保存`
- 用主动句：`服务器返回令牌`，少用「被……所……」
- 代词指代清楚；形容词克制
- 全角中文标点；引号优先 `「」` 或中文 `“”`

## 工作流

写文或改文时按此清单执行：

```text
- [ ] 标题是否直白（理解/入门/详解/教程）
- [ ] 开篇是否：定义 → 难点/价值 → 本文做什么
- [ ] 是否先场景/类比，再术语
- [ ] 章节是否一层层拆，而不是一上来细节炸弹
- [ ] 段落是否偏短、一句一意
- [ ] 配图数量达标；每图有真实文件 + 简洁 alt；无「上图是 / 图片说明」
- [ ] 工具页步骤已自动截图嵌入（无待补占位）
- [ ] 主题插图已走 Unsplash/Pexels，无合适再 AI 手绘
- [ ] 流程/架构/对比类已用 D 手绘风（非 Mermaid 默认导出）
- [ ] 手绘风是否与系列锚点一致（纸感、铅笔线、中文标签）
- [ ] 发布稿配图已上传 ImageKit 并改用 CDN URL
- [ ] 代码：该出现示例的地方是否有短代码块
- [ ] 代码是否「先说明 → 代码块 → 上面代码中……」
- [ ] 结尾是否收束，有无（完）
- [ ] 无抄袭、无冒充、软广不超过一处、未授权爬图
```

保存到仓库时：Markdown 与 `images/` 内真实文件一并交付，不得只交纯文字墙或假图片路径。

## 适用 / 不适用

**适用**：技术科普、协议/概念理解、工具教程（CSDN 等）、中文 uwarp 工具说明文

**不适用**：纯周刊链接聚合口吻、散文随笔、英文文档、需要严格学术引用的论文体

## 与文档规范的关系

需要更细的中文技术文档用词/标点时，可叠加参考 [ruanyf/document-style-guide](https://github.com/ruanyf/document-style-guide)。本 skill 侧重**博客叙事节奏 + 图文代码节奏**，不是手册条款全集。
