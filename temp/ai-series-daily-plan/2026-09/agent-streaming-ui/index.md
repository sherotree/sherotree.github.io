流式 UI（Streaming UI）解决的是体验问题：**Agent 跑 Plan-Act-Observe 可能要几十秒，用户需要看见「正在发生什么」，而不是对着空白屏猜死机了**。Token 流式输出只是其中一层；工具调用、等待人工确认、失败重试都应有可见状态。

只流最终答案，用户会在第一次 `run_sql` 时以为卡住；只显示 spinner，又不知道是在检索还是在写代码。好的流式 UI 对齐宿主的真实状态机。

下面是我整理的 Agent 界面状态：事件类型、时间线与常见坑。

流式 UI 的验收标准很简单：闭着眼听读屏，或只看时间线，能否复述 Agent 刚才做了几步、哪步失败——能，就合格。

![Agent 流式 UI 各状态](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/streaming-states_23ap8JzvQ.png)

## 一、先说一个具体麻烦

助手界面只有一个「正在思考……」转圈。半分钟后突然弹出一大段答案，中间其实调了三次工具，其中一次超时重试。

用户问：「刚才是不是错了？有没有查最新数据？」界面**无法回答**，因为中间态没渲染、没保留时间线。信任问题往往来自 UI 黑盒，而不只是答案质量。

移动端还要考虑后台切换：用户切出去一分钟再回来，界面应恢复「第 2 步正在查库」而不是重置成空白会话。

## 二、应对齐的五种界面状态

（1）**规划中（Planning）**：可选展示简短 rationale，避免长篇思维链泄露。  
（2）**工具执行中（Tool running）**：工具名、关键参数摘要、已耗时。  
（3）**流式生成（Token streaming）**：正文逐字出现，可折叠「引用来源」。  
（4）**等待确认（Awaiting approval）**：系列第十一篇 HITL 专用态，突出批准按钮。  
（5）**结束 / 失败（Done / Error）**：成功总结或可读错误 + 建议下一步。

状态应来自宿主事件，不是前端猜测。

## 三、事件协议示例

前后端宜约定统一 SSE / WebSocket 事件，便于 Plan-Act-Observe 逐步映射。

```json
{"type": "plan", "step": 2, "tool": "search_internal_docs", "summary": "检索远程办公政策"}
{"type": "tool_start", "call_id": "c-9", "tool": "search_internal_docs"}
{"type": "tool_end", "call_id": "c-9", "ok": true, "hits": 3, "duration_ms": 840}
{"type": "token", "delta": "根据手册，远程办公需"}
{"type": "await_approval", "ticket_id": "ap-1", "preview": "将发送邮件至 finance@..."}
{"type": "error", "code": "tool_timeout", "retryable": true}
```

上面代码中，同一条 `call_id` 串联起 tool 起止；`await_approval` 与 HITL 状态机共享 ticket；`error` 带 `retryable` 供 UI 决定是否展示「重试」。

前端渲染时按 `step` 排序即可还原时间线，不必再让模型「总结刚才做了什么」——那既慢又可能编。

## 四、体验细节

（1）**并行工具**：多个 `tool_start` 时显示并行条，而非覆盖。  
（2）**长输出折叠**：Observe 原始 JSON 默认折叠，展开给高级用户。  
（3）**取消**：用户中止应停宿主 loop，不是只断前端 SSE。  
（4）**断线续传**：刷新后根据 `session_id` 恢复时间线。  
（5）**首 token 时间（TTFT）与总时长**：开发态可打 metrics，优化慢工具。

产品层面可给「预计还要多久」粗提示：依据历史同工具耗时中位数，比固定 spinner 更能缓解焦虑。

## 五、和系列其他篇的关系

流式 UI 是**宿主状态机的外壳**：Plan-Act-Observe（第四篇）产生事件；工具失败（第三篇）映射为 `error` 卡片；权限拒绝（第十篇）显示明确原因；Grounding 引用（第九篇）可在 token 流结束后挂侧栏来源。

别把所有事件都折叠成一行「思考中」——那是流式 UI 最常见的偷懒实现，也是用户最不信任的那种。

## 六、常见误区

（1）**假流式：答案生成完再逐字播放**  
用户仍等全程，只是动画耍花招。  
（2）**工具名对用户不可读**  
应显示「正在检索内部文档」而非 `search_internal_docs_v2`。  
（3）**错误只 toast 一条「出错了」**  
应区分权限、超时、用户拒绝。  
（4）**思维链全文展示**  
冗长且可能含敏感推理；rationale 宜短。  
（5）**无完成态**  
流中断后界面仍显示「思考中」，永久悬挂。

Accessibility 也别忘了：状态变化除颜色外，应有文案与 aria-live，读屏用户才能感知「工具已开始 / 已失败」，而不只是看到静默的转圈。

最后，把事件流落盘：用户投诉「昨天助手删错了」时，时间线回放比让模型「回忆」更接近真相。

## 七、小结与系列导航

流式 UI 的本质：**把 Agent 闭环的每一步变成用户可见、可中断、可审计的时间线**。技术上是事件协议；产品上是信任感。系列 Agent 工程笔记至此收束于「用户看见真实进度」——黑盒越少，人对 Agent 的容忍度越高。

下一季若继续写，可以从「评测与回归」切入：闭环有了、UI 有了，怎么证明升级模型后没有悄悄变坏。

流式不等于实时：若后端 batch 完才推 token，至少在 tool 阶段诚实展示进度，别用假流式掩盖长等待。

同一界面里，历史会话与进行中的 run 应视觉区分，否则用户会把旧答案当成「刚刚还在跑的任务」。

完成态最好带耗时与步数摘要，方便用户判断这次值不值得等、要不要改问法重跑。
