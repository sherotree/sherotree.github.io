RAG（Retrieval-Augmented Generation，检索增强生成）是在模型生成之前，**先从外部知识库检索相关片段，塞进上下文，再让模型回答**。

大模型的知识来自训练数据，有截止日期、不知道你的私有文档、还可能「自信地编」。RAG 补的就是这块：**让回答有据可查，且证据来自你可控的数据源**。

下面是我整理的 RAG 最小链路：它在补什么、典型步骤与常见坑。

![RAG 填补参数化知识缺口](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/rag-knowledge-gap_927FM9cDl.png)

## 一、先说一个具体麻烦

员工问：「去年 Q3 的华东区退货率是多少？」

基座模型没读过你们内部 BI 导出，可能给一个听起来合理的数字——这就是**参数化知识（parametric knowledge）**的局限：知识 baked 在权重里，不可更新、不可审计。

RAG 的做法：先去向量库或搜索引擎里找「华东区」「Q3」「退货率」相关的报表段落，把原文塞进 Prompt，让模型**只依据这些片段**组织答案。

## 二、RAG 在补什么

简单说，RAG 补三类短板：

（1）**时效**—— 训练 cutoff 之后的信息  
（2）**私有**—— 内部文档、工单、代码库  
（3）**可验证**—— 回答能追溯到具体段落

它**不**替模型做推理，也不保证检索一定命中——检索 miss 时，模型仍可能瞎编，需要 Grounding 与拒答策略（见 Agent 工程笔记 Grounding 篇）。

## 三、典型流水线

![RAG 检索增强流水线](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/rag-retrieval-pipeline_JlXqFSI3S.png)

（A）**索引阶段（离线）**  
文档切块 → embedding → 写入向量库（可加元数据：来源、日期、权限）

（B）**检索阶段（在线）**  
用户问题 → embedding → top-k 相似 chunk（可混合关键词检索）

（C）**增强阶段**  
把 chunk 拼进 Prompt 模板，例如：

```text
依据以下文档片段回答问题。片段中没有的信息请回答「未找到」。

【片段 1】{chunk_1}
【片段 2】{chunk_2}

问题：{user_question}
```

上面模板中，片段在前、问题在后，减少模型忽略证据的概率。

（D）**生成阶段**  
模型基于增强后的上下文输出；最好带引用格式，便于核对。

### 3.1 评测检索而不只评测生成

RAG 上线前，应单独测「问题 → 是否命中正确 chunk」。生成再漂亮，检索 miss 也是空中楼阁。常用指标：Recall@k、MRR；再叠加端到端问答准确率与引用命中率。

权限与多租户场景，检索前就要按用户身份过滤 chunk——否则 RAG 会把「查得到」变成「不该看也能看到」。这与 Agent 工具权限（见 Agent 工程笔记权限篇）是同一类边界问题，只是发生在检索层。

## 四、关键环节

### 4.1 切块（Chunking）

块太大：噪声多，检索不精准。块太小：语义断掉，miss 增多。常见 256～512 token，按段落或标题切，重叠 10%～20% 避免句断。

### 4.2 检索质量

纯向量检索对专有名词、数字 ID 弱，建议**向量 + BM25 混合**，再用 rerank 模型重排 top 结果。

### 4.3 空检索处理

没命中时，应返回固定拒答，而不是让模型「尽量回答」—— 否则 RAG 退化成裸模型。

### 4.4 上下文摆放

检索片段建议放在用户问题**之前**，并在系统提示里写清「仅依据片段」。文档版本、生效日期写在元数据里，避免模型用到旧 chunk 却按新口径回答。这和 Grounding 篇的约束是同一套纪律。

## 五、和 Fine-tuning 的分工

| 手段 | 解决什么 |
| --- | --- |
| RAG | 知识从哪来、怎么更新 |
| Fine-tuning | 怎么说、什么格式、什么风格 |
| Grounding | 说了的是否真有依据 |

三者常组合使用，不是互斥选项。

## 六、常见误区

（1）**上了向量库就等于 RAG**—— 没有拒答、没有引用、没有切块策略，效果往往很差。  
（2）**chunk 越大越好**—— 塞整篇 PDF 进上下文，焦点模糊，Grounding 更难。  
（3）**忽视权限**—— 检索层不过滤 ACL，可能把 A 部门文档泄露给 B 部门用户。  
（4）**只索引不更新**—— 源文档改了，向量库不同步，回答仍引用旧版。

## 七、小结

RAG 用检索把外部知识注入上下文，补模型的时效、私有与可验证短板。索引、检索、增强、生成四步缺一不可；检索 miss 时要有拒答，命中时要有 Grounding。

Agent 工程里，RAG 常与工具调用并存：检索补文档，工具补实时数据（工单、数据库）。别把 RAG 当成唯一外部知识入口——但能私有化、可审计的静态知识，RAG 仍是默认首选。

索引更新策略也要提前想：全量重建简单但慢；增量更新快但要处理删除与版本冲突。文档一改就忘更索引，RAG 会稳定地给出**过期的正确引用**——这比未 Grounding 的胡编更难察觉。

问答质量验收要分两层：检索层「该找的 chunk 在不在 top-k」；生成层「答案是否被 chunk 支撑」。只测端到端准确率，很难定位是 embedding 差、切块差，还是 Grounding 差——分层指标能省大量盲调时间。

RAG 不是只服务问答：代码库搜索、客服工单、合规审查都在用同一套「先检索、再生成」骨架。差别在数据源、切块与权限；骨架不变，便于团队在一个概念下对齐工程分工。
