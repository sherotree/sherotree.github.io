接手陌生仓库，最浪费时间的不是读代码，是**没有地图乱逛**：打开十几个文件，仍不知道请求从哪进、数据从哪出。

用 AI onboarding 的关键，不是让它「总结一下项目」，而是**分阶段 Grounding**——先全局结构，再下钻证据，和 Agent 笔记里「检索 → 装入上下文 → 约束回答」同一路径。每一步输出都要**带文件路径、可核对、找不到就说不知道**。

新人常犯的错是：第一天就让 AI 写架构文档，文档里充满「可能」「通常」，却没有任何一行能在仓库里点开。正确顺序是**先能跑、再找入口、再跟一条链、最后才写总结**——总结是副产品，不是起点。

下面是我可复现的四步流程。四步都强调路径与核对，是因为 onboarding 的本质不是「读懂一切」，而是**快速建立可 falsify 的模型**——哪条错了，你知道该打开哪个文件。

![先画代码库地图](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/onboarding-map_Cf0Emvs36.png)

## 一、第一步：要一张地图

新开 Agent，**只 @ README + 根目录结构**（或 `tree -L 2` 输出），问：

```text
不要猜业务细节。根据现有文件回答：
1. 入口文件与启动命令
2. 路由/API 定义在哪
3. 数据层目录
4. 测试怎么跑
每项给文件路径，找不到就说未找到。
```

上面代码中，「给路径、找不到就说」减少幻觉——和 Grounding 拒答出口一样。

我会把回答存成 checklist，逐项点开文件确认存在，而不是直接相信摘要。摘要里若出现「通常」「可能」，一律当未 Grounded，回到源码查；只有带路径且点开存在的条目才进入笔记。

## 二、第二步：沿主路径下钻

![地图之后逐层下钻](https://ik.imagekit.io/4pjac7gmxh/blog/2026/09/onboarding-drill_8TfBDGE7o.png)

选定一条用户旅程，例如「登录」：

（1）`@` 路由文件  
（2）`@` handler  
（3）`@` 对应测试  

问：「从 HTTP 请求到写 session，调用链是什么？用列表，每步带文件:行号。」

**一次只下钻一条链**，避免上下文爆炸。第二条链（如「下单」）新开 thread，复用地图笔记即可。每条链的笔记单独成文，便于 `@` 精确加载——把 onboarding 做成多份小 Grounding 文档，而不是一份巨型摘要。

## 三、第三步：让 AI 产出可留存笔记

```markdown
## 登录流程（待我核对）
- POST /api/login → src/routes/auth.ts:L12
- 校验 → src/services/auth/validate.ts
- 写 session → src/middleware/session.ts
```

我人工改错后再存 `docs/onboarding/login.md`。以后新人 `@` 这份笔记，比重复问 AI 更 Grounded。

笔记里**不写业务猜测**；只写能从代码直接读到的调用关系。

## 四、第四步：用一个小改动验证理解

选低风险任务：改日志文案、补一条测试、修 typo。能独立提 PR，说明地图靠谱；卡住说明哪一层理解错了，回到那层 `@` 重问。

验证通过后再接中等任务（小 feature），不要第一天就接核心支付模块。Onboarding 的目标是**建立可核对的 mental model**，不是第一天 closing ticket；mental model 错了，后面越写越偏。

## 五、提问禁忌

（1）「讲讲这个项目」——太宽，模型会编架构。  
（2）一次 `@` 整个 `src/`。  
（3）不跑测试就相信「数据流图」。  
（4）把 AI 笔记当权威不核对源码。  
（5）跳过测试目录——测试往往是最短的真实用法文档。

若仓库极大，可以先让 AI 根据 `package.json` / `go.mod` / `Cargo.toml` 判断技术栈，再缩小 `@` 范围——仍要带路径，仍要可点开。栈猜错时，以你本地跑通的命令为准更新笔记。

## 六、和系列其他篇的关系

规则文件（系列③）提供默认约束；`@` 策略（系列④）控制每步证据量。Onboarding 是**多次短 Grounding 的串联**，不是一次长篇总结。

Debug 时（系列⑧）同样要带路径与 stack；Review 时（系列⑨）可对照 onboarding 笔记看改动是否偏离主路径。Onboarding 笔记应每月与主路径抽样核对一次，防止代码演进后笔记仍 Ground 在旧世界上。

## 七、时间盒与记录

我给自己**第一天只画地图 + 一条主路径**，不在第一天接业务 deadline。每阶段时间盒 30～45 分钟，到点仍混乱就缩小问题（例如只搞清「测试怎么跑」），而不是无限追问 AI——时间盒逼你优先 Ground 在可验证的小问题上。

记录用仓库内 `docs/onboarding/`，别只留在 chat——chat 不是 Grounding 证据，Git 里的笔记才是。核对源码时改笔记，并 commit，后续 `@` 才靠谱。第二周 onboard 的同事应能复用同一份笔记，而不是重新问 AI 猜架构。

## 八、小结

读陌生库 = **地图 → 主路径 → 笔记 → 小改动验证**。AI 是向导，源码是 ground truth；分阶段、带路径、可核对，才算 onboarding 完成。和 Grounding 一样：**找不到路径就说不知道**，比编一张漂亮架构图更安全，也比第三天才发现入口搞错更省时间。Onboarding 完成的标志，是你能向同事用五分钟讲清「请求怎么走进来、错误从哪里出去」——每句都能点开文件。达不到这一点，说明地图或主路径笔记还缺 Grounding，继续下钻比赶工接需求更划算。
